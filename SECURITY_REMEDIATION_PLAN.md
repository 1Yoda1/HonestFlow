# HonestFlow 3.0 — план устранения находок аудита

Основание: [SECURITY_AUDIT.md](SECURITY_AUDIT.md), находки HF-SEC-001…015. План составлен 28.10.2026 по текущим checkout трёх репозиториев. Это порядок локальной разработки и проверки, а не разрешение на deployment, изменение production-БД, выпуск ключей или публикацию релиза.

## Объём и критерий завершения

**Семь проходов.** Каждый проход завершается отдельной проверкой изменённой границы доверия, сборкой/целевыми тестами соответствующих компонентов и записью остаточного риска. Сквозная проверка трёх компонентов выполняется после проходов 3–5 и повторно после прохода 7. Все 15 ID распределены по одному основному проходу; связанные регрессии проверяются и в последующих проходах.

Цель — закрыть каждую находку исправлением, изменённой и явно утверждённой продуктовой семантикой либо документированным остаточным риском. Абсолютно запретить локальный обход на компьютере, полностью контролируемом его владельцем, невозможно. Серверные полномочия, сохранность ключей и предсказуемая деградация при сбоях остаются обязательными проверяемыми границами.

## Зависимости и порядок выпуска

1. В начале каждого прохода зафиксировать текущий Git diff: в HonestFlow уже есть чужие незакоммиченные изменения. Не смешивать их с исправлениями безопасности и не сбрасывать. Перед серверными изменениями читать `docs/architecture-decisions.md`, контроллер, контракт, OpenAPI и оба потребителя.
2. Изменения API/БД из проходов 3–5 делать совместимыми по этапам: сначала сервер понимает старый и новый протокол, затем обновляются HonestFlow/HonestDesk, затем после подтверждения миграции выключается старый небезопасный путь. Временная совместимость должна иметь срок удаления, а не стать постоянным обходом.
3. Тестировать только на фиктивных секретах, временной SQLite и тестовом объектном хранилище. Для ACL/TOCTOU/часов нужны отдельная Windows VM и обычная учётная запись. После каждого прохода — целевые тесты и одна сборка затронутых приложений; полноценная регрессия перед релизом.
4. Ни один проход сам по себе не означает deployment. Production API, `/opt/honestserver/HonestLicenseFull.db`, серверные секреты, ECDSA private key и живые клиентские токены не участвуют в проверках. Выпуск и миграция production требуют отдельного задания.

## Принятые решения и открытые вопросы

| Тема | Решение / следующий шаг |
|---|---|
| Сессия HF под Windows-аккаунтами | **Принято:** Service работает под одной учётной записью Windows. В проходе 1 можно перейти на `CurrentUser` с явными ACL и аккуратным выходом из старой machine-DPAPI сессии. |
| Значение флага `Service` | **Принято:** Service включает все локальные функции. HF-SEC-009 закрывается согласованием контракта, тестами и устранением вводящих в заблуждение отдельных переключателей, а не запретом функций. |
| Offline Service | **Принято:** сохранить offline grace. Мгновенный отзыв без сети невозможен; локальный срок проверяется при операциях, остаточный риск фиксируется явно. |
| Перенос устройства | **Принято:** новое устройство или перенос должны пройти повторное одобрение в HonestDesk. Installation GUID остаётся идентификатором, proof-of-possession добавляется отдельно. |
| Пароль входа и идентификационный код | **Принято:** разделить и мигрировать; чувствительные настройки выдавать при действующей Service-лицензии. Старые клиенты требуют временного совместимого перехода и ротации секретов. |
| HonestDesk: роли и разблокировка | **Открыто до прохода 3:** кто сможет просматривать заявки, менять клиентов, подписывать лицензии и публиковать обновления. Локальный пароль без серверного разделения прав не решает HF-SEC-004. |
| Подпись релизов | **Принято:** платный Windows Authenticode не используем. Манифест выпуска подписываем собственным отдельным ECDSA-ключом. Закрытый ключ не попадает в Git, API, HonestFlow или ключ лицензий HonestDesk; публичный ключ встраивается в HonestFlow. До включения обязательной проверки нужны выпуск ключа, совместимый контракт сервера и переход для уже установленных неподписанных версий. |

Для начала прохода 1 продуктовых вопросов больше нет. Если эксперимент опровергнет `Likely`-находку, это отмечается в аудите вместо внедрения ненужной защиты.

## Текущий прогресс прохода 1

На 28.10.2026 в рабочем дереве HonestFlow начаты HF-SEC-001 и HF-SEC-015:

- **HF-SEC-001 — в работе.** Новые сохранённые сессии используют `CurrentUser` DPAPI и каталог текущего Windows-пользователя; старые machine-DPAPI файлы удаляются при работе store без переноса токенов. Это потребует однократного входа в Service. Ещё нужны проверка ACL/разделения в двух Windows-профилях и решение об отзыве ранее выданных серверных refresh-сессий: удаление локального файла само по себе их не отзывает.
- **HF-SEC-015 — локально исправлено, ожидает общей регрессии.** Downloader останавливает чтение перед записью блока сверх `SizeBytes`; целевой тест проверяет остановку после первого блока и отсутствие файла.
- **HF-SEC-005 — код исправлен, проверка границы привилегий ожидает VM.** Обновлятор больше не читает исполняемый PowerShell-скрипт из ProgramData: команда передаётся через `-EncodedCommand` абсолютному системному `powershell.exe`. Backup и журнал создаются рядом с установленным EXE; после копирования обновления проверяются размер и SHA-256 именно целевого файла перед запуском. На обследованном ПК каталог `C:\Program Files\HonestFlow` доступен Users только на чтение. Для произвольного пользовательского каталога установки защищённость не доказана; её надо проверить и при необходимости запретить автообновление из такого пути. Тест с обычным пользователем/повышенным процессом в VM ещё не выполнен.

Первый тестовый запуск упёрся в TLS-ошибку NuGet при восстановлении KktBootstrap. Повторные запуски использовали уже имеющиеся helper-артефакты с `SkipKktBootstrapHelpers=true`; целевые тесты session store, downloader и self-update прошли: **18/18**. Это не подтверждает устойчивость к реальной подмене файлов между процессами; проход 1 пока не завершён и не готов к релизу.

## Подготовка прохода 2: формат и порядок включения

Манифест описывает один бинарный файл: `application`, `version`, `fileName`, `architecture`, `sizeBytes`, `sha256`. Подписываются **точные UTF-8 байты JSON**, без повторной сериализации. Ответ API должен передавать эти байты в Base64, DER-подпись ECDSA P-256/SHA-256 в Base64 и `keyId`. URL загрузки остаётся отдельным транспортным полем: его смена не меняет подписанные байты, а скачанный файл обязан совпасть с подписанными размером и SHA-256. Подпись проверяется до разбора и использования полей манифеста. Ключ выпуска отделён от ключа лицензий.

Порядок перехода: подготовить проверяющий код и тесты; создать отдельный закрытый ключ вне репозиториев и сервера; встроить соответствующий публичный ключ в новый HF; добавить совместимую публикацию и выдачу манифеста на сервере; выпустить переходную версию через контролируемый установщик; затем включить отказ от неподписанных обновлений. Если старый клиент уже доверяет подменённым метаданным API, одна лишь новая проверка в будущем клиенте не защищает первый переход — переходный установщик нужно доставить по контролируемому каналу и проверить отдельно. Ротация требует заранее встроенного следующего публичного ключа. Откат допускается только на отдельно подписанную и явно разрешённую версию; простой пониженный номер версии отклоняется.

Локальная подготовка: `ReleaseManifestVerifier` проверяет DER-подпись ECDSA P-256/SHA-256 исходных байтов и возвращает только проверенные поля. Целевые тесты проверяют корректный выпуск, подмену размера, чужой ключ, неизвестный `keyId`, отсутствие подписи, чужой компонент и архитектуру. Отдельная консольная утилита `tools/HonestFlow.ReleaseSigning` создаёт зашифрованный ключ вне Git, подписывает и публикует файл через presigned PUT Cloud.ru; её выход принят HF в сквозном тесте. На этой Windows импорт зашифрованного PKCS#8 через CNG не прошёл тест, поэтому утилита использует `ExportECPrivateKey` внутри процесса и хранит его в версионированном файле, зашифрованном PBKDF2-HMAC-SHA256/AES-256-GCM.

Серверный код принимает только проверенный подписанный манифест, выдаёт временную PUT-ссылку для `releases/`, после загрузки сам потоково проверяет размер и SHA-256 и лишь затем создаёт immutable `ComponentAsset`. Несовпадающий объект удаляется, незавершённые загрузки очищаются через 24 часа. Выдача идёт по короткоживущей GET-ссылке Cloud.ru; старые direct/Yandex записи сохранены как переходный fallback на сервере. HF проверяет подписанные метаданные и для самообновления, и для установщиков компонентов. Проверки: HF **757/757**, сервер **77/77**, HonestDesk **37/37**.

Production-ключ `release_6bd64214975e48a3af2c20b8` создан пользователем вне Git; закрытая часть осталась в зашифрованном локальном файле, публичная встроена в `ReleaseTrustStore`. В production-композиции HF включён обязательный отказ от неподписанных манифестов. Осталось выполнить отдельный серверный code+database deployment, настроить публичный ключ через подготовленный script, опубликовать подписанный переходный HF и перенести компонентные дистрибутивы. До сквозной проверки фактического выпуска HF-SEC-006 остаётся открытой.
