# Security gate HonestFlow 3.0.1-beta

Актуализировано: 5 ноября 2026 года.

Это выпускной гейт, а не повторный аудит. Он фиксирует решение по 15 находкам
из `SECURITY_AUDIT.md`, выполненные исправления и три оставшиеся ручные
проверки перед публикацией beta. Production в рамках этих работ не проверялся
и не изменялся.

## Итоговое решение

Кодовые блокеры beta закрыты. До выпуска нужны только контролируемые ручные
проверки на тестовой Windows и обычный выпускной checklist из Issue №3.

| Блокер | Результат | Проверка |
| --- | --- | --- |
| `HF-SEC-003` | Обычная конфигурация больше не содержит identification code и CHZ token; Service-секреты выдаёт отдельный Service endpoint после проверки права. | Server integration tests `133/133`, HonestFlow tests `768/768`. |
| `HF-SEC-008` + `HF-SEC-010` | Каждая Service-операция заново учитывает срок grant/offline grace; отсутствие policy запрещает Service только в Service-пути. Периодическая проверка лицензии выполняется каждые 15–20 минут. | HonestFlow tests `768/768`, server integration tests `133/133`. |
| `HF-SEC-011` | Refresh rotation сериализована SQLite write-transaction; повтор replaced token отзывает всю token family. | Server integration tests `133/133`, включая replay и отзыв выданного access token. |
| `HF-SEC-013` | HonestDesk скачивает диагностику во временный `.part`, сверяет размер и SHA-256 из защищённого каталога API и только затем открывает файл. При ошибке временный файл удаляется. | HonestDesk tests `47/47`, включая верный файл, неверный размер, неверный и недопустимый hash. |

## Обязательные ручные проверки перед beta

1. **HF-SEC-001 — граница профилей Windows.** Войти в Service под первым
   обычным профилем, затем проверить, что второй обычный профиль не получает
   сессию первого и запрашивает свой вход.
2. **HF-SEC-005 — безопасное самообновление.** В тестовой VM запустить
   обновление из непривилегированного профиля; подтвердить успешный проверенный
   переход и отказ при небезопасном каталоге установки либо подмене файла.
3. **HF-SEC-006 — сквозной доверенный релиз.** На тестовом устройстве пройти
   обновление HonestFlow и установку одного компонентного дистрибутива;
   отдельно подтвердить отказ при подменённом manifest, signature или SHA-256.

## Осознанно после beta

| ID | Решение | Граница принятого риска |
| --- | --- | --- |
| `HF-SEC-002` | Proof-of-possession устройства после beta. | Сейчас `DeviceId` — предъявляемый идентификатор; перенос устройства остаётся через повторное одобрение HonestDesk. |
| `HF-SEC-004` | Усиление локальной админ-границы после beta. | CurrentUser DPAPI не защищает от процесса того же Windows-пользователя; HonestDesk остаётся доверенным однопользовательским клиентом. |
| `HF-SEC-007` | Усиление защищённого времени после beta. | Offline grace сохранён по продуктовому решению; clock anchor можно удалить при полном контроле ПК. |
| `HF-SEC-009` | Закрыто продуктовым решением. | Право `Service` включает все локальные Service-функции; legacy-флаги не являются отдельной границей полномочий. |
| `HF-SEC-012` | Измеряемый load baseline и bounded concurrency после beta. | Уже действует лимит 10 попыток в минуту на IP. |
| `HF-SEC-014` | Пагинация и лимиты масштаба после beta. | Действующие списки и rate limits достаточны для малой beta, но не для масштабирования. |
| `HF-SEC-015` | Исправлено. | `VerifiedAssetDownloader` прекращает чтение до записи блока сверх заявленного размера; есть regression test. |

## Порядок выпуска

1. Выполнить три ручные проверки выше и сохранить их результат в Issue №13.
2. Прогнать полные тесты HonestFlow, HonestDesk и HonestLicenseServer на
   финальных `develop`-ревизиях.
3. Пройти выпускной checklist из Issue №3.
4. Только после этого сформировать подписанный 3.0.1-beta дистрибутив и
   провести отдельное, явно разрешённое развёртывание API перед обновлением
   клиентов.

## Что этот документ не утверждает

- Он не подтверждает состояние production и не требует обращения к production-БД.
- Отложенные пункты не объявлены исправленными: для них указан владелец риска
  и следующий этап.
- Платный Authenticode не требуется: доверие к обновлениям основано на
  собственной ECDSA-подписи manifest и обязательной локальной проверке файла.
